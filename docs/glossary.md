# 术语表维护

## 日常操作

术语表的唯一内容来源是 `data/glossary.md`。网站 `/SRD/edit/?path=glossary` 的“术语表”入口可以搜索、新增、修改、启停和删除条目，也可以切换“编辑 Markdown”直接维护文件。表单和 Markdown 修改的是同一份内容，不再维护 YAML 或 JSON 副本。

日常修改只需在 editor 点击“保存并发布”，由服务器执行格式检查、来源校验、完整构建、版本记录和后台 Git 同步。可以与规则正文一起发布；任何一项失败都不会覆盖正式文件和站点。功能代码首次上线后，后续术语维护无需手工修改源码或执行部署命令。

未发布修改保存在当前浏览器会话，切换章节时保留，刷新前会提示。发布携带术语表原始版本号，遇到别人更新时展示版本冲突并保留本地草稿。删除需再次点击确认，并在发布后才影响读者。

## 解释的来源

术语解释只能是规则原文，或用户明确审核通过的文案。不得自行概括，也不能把翻译备注当成解释。

- 原文：选择来源页面及中英文对应小节，选择连续段落，点击“引用所选原文”。构建会逐字核对对应正文，只允许完整连续段落或列表项；去排版标记和规范空白，不改措辞。正文和摘录可一起修改、一起发布。
- 人工文案：编辑解释后，由用户本人展开“人工审核改写文案”，填写审核人，点击“我已审核，批准此文案”。Editor 记录审核人、日期及对应内容的指纹。名称、来源或解释发生变化，审核记录失效，必须重新审核。
- 待审核或缺少来源的条目可以保存为停用状态；启用时必须通过双语解释校验。

审核记录是现有受密码保护 editor 中的人工确认记录，不是新的身份认证系统。代理不得代用户点击审批，也不得自行填写审核记录。初始 14 条均使用原文；没有自动批准的解释。

原文选择器显示上次发布的正文。若同一批次中也修改正文，可把对应新原文直接填写到解释中，最终构建会对照本次候选正文校验。发布成功后来源选择器会刷新。

## Markdown 格式

每个二级标题是一条术语：`## 中文名称 {#唯一标识}`。标题后的中文字段记录英文名、别名、大小写规则、启停状态、来源页面、中英文小节及审核记录。别名用中文分号 `；` 分隔。三个固定三级标题分别是“翻译备注”“中文解释”“英文解释”。二三级标题保留给格式结构，解释正文使用段落。

新增条目可在表单创建，再切换 Markdown 查看完整模板。标识保持稳定且全表唯一；启用条目不能有互相冲突的名称或别名。停用条目保留译名和翻译备注，不会标注到阅读站。删除最后一条术语也是合法操作，会关闭所有术语提示。

英文的大小写策略与变体可在表单中维护。修改审核后的文字不会自动生成新审核指纹；若手工改 Markdown，需要回 editor 重新人工审核。原文摘录被正文修改影响时，发布会报错，需同步核对。

## 初始来源

初始名称、译名、变体、大小写策略及翻译备注来自用户提供的 `Daggerheart-translator/skills/daggerheart-translation-pipeline/resources/terms-14448.json`，共 328 条；源文件 SHA-256：`5599B2E3D9177E3FAE15881AFDB2425B4ADDA8BA7CEDD988317423D0AEEAFBB6`。其中 14 条有明确的中英文规则出处并已启用，其余 314 条停用待完善。此后以可人工维护的 Markdown 为准，构建不依赖翻译仓库。

中英文历史标题锚点有部分错位，来源选择器按实际标题列出小节。不要仅凭锚点拼写推断含义。

## 技术验证

Editor 与构建 CLI 共用 `static/js/glossary-core.mjs` 解析和序列化 Markdown。发布接口仅额外允许精确路径 `data/glossary.md`，不开放整个 data 目录。中文原文来自 `src/pages/**/zh.md`，英文来自 `src/pages/**/en.md`。

运行 `python scripts/build_srd.py`、`python -m pytest -q`、`npm test` 和 `npx playwright test --workers=2`。浏览器发布测试拦截保存请求，不修改真实内容；后端真实构建和发布验证在隔离临时目录进行，不推送远端。
