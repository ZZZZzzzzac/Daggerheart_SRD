# PRD：SRD 站点完整翻新

## Problem Statement

当前 SRD 站点已经具备中英双语 Markdown、Hugo 静态构建、静态部署和在线编辑能力，但它更像一组逐步叠加的脚本与页面，而不是一个可靠、易查、易维护的文档系统。

普通读者在长页面中查找规则时缺少整站导航和正文搜索。移动端会先展示很长的本页目录，正文被推到首屏之外。页面依赖过时的前端组件，版式、表格和高密度规则内容也没有形成稳定的视觉层次。当前标题位置由浏览器随机生成，刷新后链接可能失效，搜索、分享和段落级反馈都无法可靠定位。

管理员虽然可以在线修改正文，但保存会先覆盖正式内容，再尝试直接重建线上目录。构建失败时，正式源文件和线上产物可能处于不一致状态；多人先后编辑同一页面时也可能互相覆盖。GitHub 备份失败会被忽略，编辑器预览与正式构建还使用不同的 Markdown 转换规则。

此外，目录和标题信息在多处重复维护，搜索、术语跳转和站内反馈尚未建立。官方 SRD 大版本更新频率很低，但每次更新都需要从完整中英文文档重新建站；当前流程没有把“大版本整体重建”和“版本内日常勘误”明确分开。

本次工作需要把站点翻新为一个以规则查询和长文阅读为核心、可以安全在线维护的文档系统，而不是只更换网页皮肤。

## Solution

保留静态站和双语 Markdown 的总体方向，以整体简单度为技术选择原则，重构内容构建、发布服务和阅读界面。

每个官方 SRD 大版本以完整的中文 Markdown、英文 Markdown和一份章节清单为输入，经过完整性检查后重新生成站点。大版本之间允许破坏性更新，线上永远只提供最新版，不要求兼容旧页面地址或合并旧版勘误。进入某个大版本后，拆分页面成为日常勘误的正式内容，小节链接在该版本生命周期内保持稳定。

构建系统从唯一章节清单生成 CHM 式整站目录、页面顺序、面包屑、前后页和搜索元数据。内容构建核心统一处理 Markdown 渲染、固定小节定位、目录、断链、搜索资料及术语链接，并在完整构建成功后才产生可发布站点。

阅读界面采用单一左侧折叠目录，目录最深展示到小节。桌面端固定显示，移动端改为抽屉；正文不再被目录推离首屏。站点提供默认中文、手动中英文切换、深浅主题、本地全文搜索、页面与小节级反馈入口，并以 HTML、CSS 和少量交互脚本完成视觉升级。

在线编辑器只修改正文。它沿用阅读站的顶部标题栏和左侧 CHM 目录，仅将正文区域替换为编辑区和预览区；编辑工具取代阅读模式的搜索框。从某篇正文进入编辑器时默认打开该页面，编辑器内也按同一目录切换章节。保存时检查页面版本，避免覆盖他人修改；预览和正式站使用同一套渲染规则。每次保存都在临时位置完整重建全站，全部检查通过后才一次性替换正式内容和线上产物。成功发布必须先在服务器本地形成 Git 版本记录，再异步推送 GitHub；远端故障不阻塞发布，但必须告警并自动重试。

读者勘误进入站内反馈收件箱，不依赖 GitHub。读者无需登录，联系方式选填；管理员使用现有公用密码进入后台，以待处理、处理中、已采纳和已关闭四种状态管理反馈。反馈不会直接修改正文。

## User Stories

1. 作为中文读者，我希望首次进入站点时直接看到中文内容，以便立即开始阅读。
2. 作为双语读者，我希望在同一页面地址切换中英文，以便对照规则而不必重新查找页面。
3. 作为回访读者，我希望站点记住我主动选择的语言，以便下次继续使用相同语言。
4. 作为规则查询者，我希望从一个 CHM 式目录浏览全站页面与小节，以便快速理解内容结构。
5. 作为规则查询者，我希望目录默认只展开当前页面的小节，以便看清当前位置而不被过长目录淹没。
6. 作为规则查询者，我希望手动展开其他页面的小节，以便在跳转前查看目标页面包含什么。
7. 作为规则查询者，我希望当前页面和当前小节在目录中清楚高亮，以便随时确认阅读位置。
8. 作为桌面读者，我希望目录固定在正文左侧并始终显示，以便随时查看当前位置和跳转规则。
9. 作为手机读者，我希望目录通过抽屉打开，以便正文进入首屏而不是先显示整段目录。
10. 作为读者，我希望正文顶部显示简短的当前位置路径，以便快速返回上级页面。
11. 作为顺序阅读者，我希望页底提供上一页和下一页，以便按章节顺序连续阅读。
12. 作为长文读者，我希望正文保持舒适行宽、行高和段落间距，以便长时间阅读。
13. 作为规则查询者，我希望规则块、示例、贤者恩泽、警告、表格和数据卡具有稳定的视觉区别，以便快速扫描信息。
14. 作为手机读者，我希望宽表格可以横向滚动，以便数据不会被压缩到无法阅读。
15. 作为读者，我希望选择浅色或深色主题，以便适应不同环境。
16. 作为回访读者，我希望站点记住我的主题选择，以便下次无需重新设置。
17. 作为读者，我希望站点不依赖第三方 CDN 才能显示正文、目录或搜索，以便外部服务故障时仍可查阅规则。
18. 作为读者，我希望即使增强脚本加载失败，核心正文仍然可读，以便基础阅读不被交互故障阻断。
19. 作为规则查询者，我希望搜索页面标题、小节标题和正文，以便从记得的任何片段找到规则。
20. 作为规则查询者，我希望页面标题命中优先于小节标题，小节标题命中优先于正文命中，以便最明确的结果排在前面。
21. 作为规则查询者，我希望同一小节的多次命中合并成一条结果，以便长章节不会淹没结果列表。
22. 作为规则查询者，我希望结果显示最相关的正文摘要，并严格按相关程度排序，以便最可能需要的规则出现在前面。命中次数只作为调试信息，不在页面展示。
23. 作为规则查询者，我希望搜索结果直接跳到具体小节，以便不必在长页面中再次寻找。
24. 作为双语读者，我希望搜索默认只查当前语言，并能切换另一语言，以便减少无关结果。
25. 作为注重隐私的读者，我希望搜索完全在浏览器本地完成，以便查询词不会被服务器收集。
26. 作为规则新手，我希望已登记规则术语的首次出现可以跳到定义，以便快速理解陌生概念。
27. 作为读者，我希望同一小节的重复术语不会全部变成链接，以便正文保持清爽。
28. 作为内容维护者，我希望歧义词、标题、代码、已有链接和明确排除的位置不会被自动加链接，以便避免错误跳转。
29. 作为内容维护者，我希望术语链接只使用专门维护的规则术语表，以便翻译工具中的大量工作术语不会污染正文。
30. 作为读者，我希望能够从页面或具体小节提交勘误，以便准确指出问题位置。
31. 作为无法使用 GitHub 的读者，我希望直接在站内提交反馈，以便不受第三方账号和网络条件限制。
32. 作为反馈者，我希望无需登录即可提交纯文字反馈，以便降低参与门槛。
33. 作为反馈者，我希望联系方式可以选填，以便自行决定是否接受后续联系。
34. 作为反馈者，我希望提交内容自动附带语言、页面、小节位置和站点版本，以便无需手工描述上下文。
35. 作为管理员，我希望在受密码保护的后台看到新反馈和未读数量，以便集中处理勘误。
36. 作为管理员，我希望把反馈标记为待处理、处理中、已采纳或已关闭，以便追踪处理进度。
37. 作为管理员，我希望给反馈添加内部备注，以便记录判断依据和后续动作。
38. 作为管理员，我希望反馈不能直接修改正文，以便内容发布仍经过编辑和构建检查。
39. 作为管理员，我希望编辑器只允许修改正式正文页面，以便章节结构和术语配置仍通过更严格的仓库流程变更。
40. 作为管理员，我希望使用团队公用密码进入编辑器，并填写自己的显示名称，以便保持简单认证同时留下轻量修改记录。
41. 作为管理员，我希望加载页面时记住版本，并在保存前检查版本，以便不会无意覆盖另一位管理员的修改。
42. 作为管理员，我希望发生版本冲突时看到双方差异并重新合并，以便保留两边有效修改。
43. 作为管理员，我希望编辑预览与正式站使用同一套 Markdown 规则，以便保存前看到可信结果。
44. 作为管理员，我希望保存失败时看到明确、可操作的错误，以便知道需要修复什么。
45. 作为管理员，我希望构建失败时正式正文和线上站点完全不变，以便错误内容不会造成半发布状态。
46. 作为管理员，我希望一次保存会完整检查目录、小节位置、断链、搜索和术语目标，以便局部修改不会破坏全站。
47. 作为管理员，我希望成功版本一次性替换线上版本，以便读者不会看到新旧文件混杂。
48. 作为管理员，我希望每次成功发布先留下本地 Git 版本，以便 GitHub 暂时不可用时仍有可追溯历史。
49. 作为管理员，我希望 GitHub 同步失败时收到明确提示，并由系统自动重试，以便异地备份不会静默丢失。
50. 作为管理员，我希望 GitHub 故障不阻塞已经通过全部本地检查的勘误发布，以便外部服务不影响站点维护。
51. 作为维护者，我希望章节标题、层级、顺序和页面元数据只维护一份，以便导航、编辑器和搜索不会失同步。
52. 作为维护者，我希望页面与小节位置在当前大版本内保持稳定，以便搜索、分享和反馈链接长期有效。
53. 作为维护者，我希望构建发现重复小节位置、无效目标或断链时直接失败并列出问题，以便缺陷不会进入正式站。
54. 作为维护者，我希望技术组件只有在明显降低复杂度或解决现有方案无法解决的问题时才被替换，以便系统保持简单。
55. 作为维护者，我希望所有正式运行所需的字体、样式、脚本和索引由本站自行部署，以便发布不依赖第三方运行时服务。
56. 作为大版本发布者，我希望用完整中文 Markdown、完整英文 Markdown 和新版章节清单重新生成站点，以便低频大更新不必手工逐页迁移。
57. 作为大版本发布者，我希望任一章节缺少中文或英文时停止生成，以便只有翻译完整的版本才能发布。
58. 作为大版本发布者，我希望大版本生成可以整体替换旧版页面和地址，以便不为低频更新承担长期兼容成本。
59. 作为大版本发布者，我希望线上永远只提供最新 SRD，以便读者不会误查旧规则。
60. 作为大版本发布者，我希望旧版本通过 Git 标签或发布归档保留，以便必要时仍能追溯历史内容。
61. 作为维护者，我希望用一条本地命令启动完整站点进行验收，以便无需维护远程预览环境。
62. 作为维护者，我希望逻辑模块通过自动化测试，最终视觉由人工验收，以便测试关注稳定行为而不是脆弱像素细节。

## Implementation Decisions

### 内容版本与真相源

- 区分“大版本整体生成”和“版本内日常编辑”两条流程。
- 每次大版本以完整中文 Markdown、完整英文 Markdown 和一份章节清单为输入，生成一套全新的正式内容。
- 大版本生成是破坏性的，不合并上一版本的在线勘误，不保证旧页面地址或旧小节位置继续有效。
- 线上只提供最新大版本；旧版本仅通过 Git 标签或发布归档保留，不部署可访问的历史站点。
- 一个大版本发布后，拆分页面是该版本日常编辑的正式内容源；整本 Markdown 不参与日常发布。
- 每个列入章节清单的页面必须同时存在中文和英文内容，缺少任一语言时禁止生成或发布。

### 唯一章节清单

- 建立一份唯一章节清单，维护页面路径、双语标题、层级、顺序和发布状态。
- CHM 目录、移动端目录、编辑器共用目录、当前位置路径、前后页及搜索页面元数据全部从该清单生成。
- 模板和编辑器脚本不得另行维护页面标题或顺序副本。
- 在线编辑器不提供章节清单管理；章节结构变更通过仓库提交完成。

### 内容构建核心

- 提取一个可独立测试的内容构建核心，以“版本内容、章节清单和可选规则术语表”为输入，以“完整站点产物和结构化诊断”为输出。
- 内容构建核心统一负责 Markdown 转换、内容组件、页面生成、固定小节位置、目录、搜索资料、术语链接和链接校验。
- 编辑器预览调用相同的 Markdown 转换与内容组件规则，不再维护另一套近似渲染器。
- 构建发现缺失语言、重复小节位置、无效页面、无效术语目标或断链时返回失败，不生成可发布版本。
- 页面增强不应成为正文可读的前置条件；核心 HTML 必须由静态构建直接产生。

### 页面地址和小节位置

- 本次翻新及以后大版本更新允许改变页面地址，不承担跨大版本兼容责任。
- 同一大版本内，页面地址和重要小节位置必须稳定。
- 中英文共用同一页面地址和同一个语言无关的小节位置。
- 小节标题文字变化不得自动改变已确认的位置名。
- 只在当前大版本内维护位置别名；切换大版本后可重新生成。

### 阅读界面

- 使用单一 CHM 式整站目录，不设置独立右侧小节目录。
- 目录同时包含页面和小节；当前页面自动展开，其他页面默认折叠并可手动展开。
- 点击页面进入页面，点击小节直接定位；当前页面和当前小节需要明确高亮。
- 桌面端目录固定在左侧并始终显示；移动端目录使用抽屉，不在正文前完整展开。
- 正文顶部保留简短当前位置路径，页底保留上一页和下一页。
- 中英文继续共用同一页面地址。首次访问默认中文，只记住用户主动做出的语言选择，不根据浏览器语言自动判断。
- 支持浅色和深色主题，默认跟随系统，手动选择后记住设置。
- 视觉升级以 HTML、CSS、字体、排版、颜色和内容组件为主；首版不依赖新增插画。
- 支持当前主流桌面和手机浏览器，移除旧版 IE 兼容逻辑。
- 字体、样式、脚本和搜索索引全部本站托管，不依赖第三方 CDN。
- 技术栈默认保留现有静态站方案；只有在能明确降低整体复杂度或解决现有方案无法解决的问题时才替换组件。

### 搜索

- 搜索索引在构建期按语言生成，查询在浏览器本地执行。
- 索引覆盖页面标题、小节标题和正文。
- 排序权重依次为页面标题、小节标题和正文；具体搜索实现必须用中英文样本验证该排序。
- 搜索结果以小节为单位，同一小节的多次命中合并为一条结果，显示最相关摘要并按相关程度排序；命中次数只保留给调试，不在页面展示。
- 结果直接跳到命中小节的固定位置。
- 默认搜索当前语言，允许手动切换另一语言。
- 支持正确文字的连续匹配、部分词和完整短语；不实现错别字猜测或模糊纠错。
- 不记录搜索词，也不加入访问或行为统计。
- 搜索库不预先锁定；选择时以中文匹配质量、索引体积、本地部署便利和整体复杂度为依据。

### 规则术语链接

- 只使用维护者之后提供的专用规则术语表，不导入或复用 ParaTranz 翻译术语表。
- 术语表由仓库维护，不在在线编辑器中提供管理界面。
- 同一小节只自动链接每个术语第一次出现的位置。
- 优先匹配更长术语，不处理标题、代码、URL、已有链接或明确排除的位置。
- 中英文分别匹配，共用已验证的目标页面和小节位置。
- 歧义词可以关闭自动链接；目标不存在时构建失败。
- 术语表未交付前，构建能力可以完成并通过测试，但自动链接默认关闭，不阻塞新版上线。

### 在线编辑与发布

- 提取一个可独立测试的发布协调模块，以“页面路径、编辑内容、加载时版本和自报名称”为输入，返回成功版本或明确失败原因。
- 在线编辑器只允许读取和修改正式正文页面，不允许修改章节清单、规则术语表或基础设施文件。
- 编辑器复用阅读站的顶部栏和左侧目录；顶部编辑工具替换搜索框，正文区域替换为 Markdown 编辑区和正式规则预览区。
- 从正文页进入编辑器时必须通过页面地址自动打开对应章节；直接打开编辑器时使用来源页面，无法判断来源时打开目录第一篇。
- 继续使用 nginx 公用密码认证，不建设个人账号或角色系统。
- 编辑成员填写显示名称并保存在浏览器中；该名称写入发布记录，但不被视为可信身份。
- 页面加载时返回内容版本；保存时若版本已变化，拒绝覆盖并提供差异信息。
- 保存先写入隔离的候选内容，在临时发布目录完整构建全站并执行全部校验。
- 只有完整构建通过后，才一次性切换正式正文和线上站点；任何失败都不得改变正式内容或线上产物。
- 每次成功发布先形成服务器本地 Git commit，再异步推送 GitHub。
- GitHub 不进入在线发布的阻塞链路。推送失败必须记录、在后台显示并自动重试，禁止静默忽略。
- 管理后台不提供历史版本浏览或回退界面；高级恢复由维护者直接使用 Git 完成。
- 每次保存完整重建全站，不实现局部页面发布。

### 站内反馈收件箱

- 提取一个可独立测试的反馈收件箱模块，负责公开提交、持久化、查询、状态流转和内部备注。
- 读者无需登录即可提交纯文字反馈，联系方式选填，不允许上传附件。
- 提交自动记录语言、页面、小节位置、站点版本和提交时间。
- 公共入口实施请求频率限制、内容长度限制和不依赖第三方服务的反机器人检查。
- 反馈保存在服务器 SQLite 数据库中，不进入静态内容，也不提交到公开仓库。
- 提供 JSON 导出和可纳入服务器备份流程的数据库备份方式。
- 管理员使用现有公用密码访问收件箱。
- 反馈状态为待处理、处理中、已采纳和已关闭；支持内部备注和状态时间记录。
- 首版只在后台显示未读数量和新反馈标记，不接入邮件、飞书或其他站外通知。
- 反馈不能一键写入正文；采纳后仍由管理员进入编辑器修改并发布。

### 本地验收与正式发布

- 提供一条本地启动命令，运行完整阅读站点及必要的本地服务供维护者验收。
- 不建设远程预览环境。
- 大版本发布前必须在本地验证目录、双语完整性、搜索、移动端布局和主要内容组件。
- 验收后以一次性切换方式发布正式最新版。

## Testing Decisions

### 测试原则

- 自动化测试只验证模块对外可观察的行为和生成结果，不绑定内部函数拆分、具体库或模板实现。
- 构建与发布测试使用临时内容和临时发布目录，不修改真实正文或线上产物。
- 对失败路径的要求与成功路径同等重要，尤其验证失败后正式状态完全不变。
- 搜索测试使用固定中英文样本验证排序、摘要、合并和跳转目标，不依赖搜索库内部评分数值。
- 视觉效果以维护者本地人工验收为准，不编写像素截图或脆弱的样式细节测试。

### 自动化覆盖范围

- 大版本导入：完整中英文输入、缺失语言、章节拆分、无效章节清单、校验失败不替换当前版本。
- 内容构建核心：Markdown 与内容组件渲染、目录生成、当前版本内固定小节位置、重复位置、断链、无效术语目标和完整站点产物。
- 搜索：页面标题优先、小节标题次之、正文再次、同小节结果合并、摘要选择、语言隔离和固定位置跳转。
- 规则术语：最长词优先、每小节首次链接、排除标题与代码及已有链接、歧义词关闭、中英文隔离和无效目标失败。
- 在线发布：合法保存、空内容、路径边界、真实目录归属、符号链接越界、版本冲突、构建失败、校验失败、一次性替换、本地版本记录、GitHub 失败告警与重试。
- 反馈收件箱：合法提交、长度限制、频率限制、恶意输入、SQLite 持久化、状态流转、内部备注、后台权限和 JSON 导出。
- 阅读界面：少量浏览器行为测试覆盖 CHM 目录展开与高亮、搜索跳转、语言切换、主题切换、移动端抽屉、当前位置路径和前后页。
- 端到端发布：从编辑一页到完整构建、线上版本切换、搜索索引更新和反馈位置仍可解析的主流程。

### 现有测试先例

- 仓库已有基于 pytest 的代理服务行为测试，覆盖合法路径、目录穿越、非正文路径、文件读写、页面列表和基础 HTTP 接口。
- 新测试沿用 pytest、临时目录和真实本地 HTTP 测试服务器的方式扩展。
- 现有测试需要保留并提升到新的发布协调接口下，避免只替换实现而丢失已有安全行为。

### 人工视觉验收

- 桌面、平板和手机尺寸下，正文应进入首屏，目录不得把正文整体推离视口。
- 当前页面和小节在目录中容易识别，长目录展开和收起行为清楚。
- 中英文正文、规则块、贤者恩泽、表格、数据卡和图片在浅色与深色主题下保持清晰。
- 长页面滚动、宽表格、搜索面板和移动端抽屉没有明显卡顿或遮挡。
- 页面整体呈现为高频查询和长文阅读工具，而不是宣传落地页。

## Out of Scope

- 兼容当前旧站或不同官方大版本之间的页面地址、小节位置和外部链接。
- 在线提供或持续维护历史 SRD 版本。
- 大版本更新时自动合并旧版在线勘误。
- 为章节清单或规则术语表开发在线管理界面。
- 使用 ParaTranz 翻译术语表作为规则术语来源。
- 每位管理员的独立账号、角色权限、密码找回或可信身份审计。
- 实时协同编辑、多人光标或自动合并冲突。
- 管理后台中的历史版本浏览、一键回退或 Git 操作界面。
- 反馈直接修改正文或自动发布。
- 反馈附件上传、强制联系方式或第三方账号登录。
- 邮件、飞书或其他站外反馈通知。
- 远程预览站或公开测试环境。
- PWA、安装式应用、完整离线阅读包或离线更新。
- 错别字容错和模糊搜索。
- 访问统计、搜索词统计、行为分析或相关 Cookie 系统。
- 无障碍专项设计、标准认证或无障碍验收门槛。
- 新主题插画和装饰性美术资源。
- 旧版 Internet Explorer 兼容。
- 为现代化而强制迁移到特定前端框架、完整 CMS、服务端搜索或常驻数据库式内容系统。

## Further Notes

### 交付顺序

1. 明确大版本输入、章节清单、版本内小节位置和生成产物的构建契约。
2. 完成可独立测试的大版本导入与内容构建核心。
3. 完成安全发布协调、版本冲突保护、正式规则预览和 GitHub 异步备份。
4. 重做阅读界面，完成 CHM 目录、正文排版、移动端、语言与主题。
5. 完成本地搜索，并预留默认关闭的专用规则术语链接能力。
6. 完成 SQLite 反馈收件箱和管理员处理后台。
7. 运行完整自动化测试，在本地进行视觉与内容验收后一次性替换正式站。

### 上线门槛

- 所有列入章节清单的页面均有完整中英文内容。
- 完整构建、结构检查、链接检查和自动化测试全部通过。
- 在线保存的构建失败、版本冲突和 GitHub 故障路径均经过验证。
- 标题和正文搜索能按预期排序并跳到具体小节。
- 桌面和手机均可在首屏开始阅读，单一 CHM 目录工作正常。
- 浅色和深色主题完成维护者人工视觉验收。
- 反馈可以提交、查看、流转和导出，且不会直接影响正式正文。

### 待提供资料
