# SRD 站点翻新技术评估

> 状态：调研结论  
> 日期：2026-09-02  
> 范围：现有仓库的建站方式、阅读体验、搜索、在线编辑、关键词跳转与反馈能力

## 1. 结论

不建议推倒整个项目重做。

应保留 Hugo、双语 Markdown、静态部署和现有在线编辑器的总体方向，同时重做以下两层：

- **前端外壳**：模板、整站导航、CSS、交互和移动端布局。
- **内容构建层**：内容真相源、稳定锚点、搜索索引、关键词索引和原子发布流程。

可以将本次翻新定义为：**保留内容资产和静态站架构，重构站点外壳与构建管线。**

不建议仅在现有 CSS 上继续打补丁，也不建议为了现代化而迁移到 React、Next.js 或完整 CMS。这些迁移会增加依赖、部署和维护成本，但不会自动解决整站目录、稳定链接、内容一致性和安全发布等核心问题。

## 2. 为什么 Hugo 仍然适合

当前 `src/pages/` 下共有 36 个 Markdown 文件，总体积约 1.5 MB。对于以阅读和查询为主的 SRD，静态站仍然是最直接的方案：

- 页面加载快，服务器资源消耗低。
- 适合在构建期生成整站目录、全文索引和关键词索引。
- 不需要数据库或服务端搜索。
- 页面直链、搜索引擎收录和离线缓存实现简单。
- 现有 1 核 1 GB VPS 足够承载静态站和轻量编辑接口。
- 现有 Markdown 内容与 Hugo 的契合度较高，无需迁移内容格式。

Hugo 本身不是当前问题的来源。主要问题是 Hugo 前方存在一层职责混杂的自制转换逻辑，前端则仍然依赖 Bootstrap 3 和 jQuery。

## 3. 当前仓库概况

当前主要链路为：

```text
src/pages/**/*.md
        ↓
scripts/build_srd.py
        ↓
content/（生成）
        ↓
Hugo
        ↓
public/（部署产物）
```

在线编辑链路为：

```text
/SRD/edit/
    ↓ POST /api/save
scripts/proxy_server.py
    ↓
覆盖 src/pages 中的文件
    ↓
调用 build_srd.py 和 Hugo
    ↓
直接更新 public/
```

现有方案已经具备双语内容、按页面拆分、静态发布和在线编辑器雏形，因此没有必要放弃全部已有工作。

## 4. 主要结构问题

### 4.1 内容真相源不明确

仓库同时存在：

- `src/pages/**/*.md`
- `src/DH-SRD-CN.md`
- `src/DH-SRD-EN.md`

正式构建和在线编辑使用 `src/pages/`，但 `scripts/split_pages.py` 会先清空整个 `src/pages/`，再根据整本 Markdown 重新生成页面。

这意味着：如果大更新时重新运行拆分脚本，在线编辑器积累的勘误和局部修改可能被直接覆盖。

建议明确以下规则：

> `src/pages/` 是唯一正式内容源。整本 Markdown 只能作为外部导入源；导入工具必须生成差异并经过人工确认，不得直接清空或覆盖正式页面目录。

### 4.2 目录信息重复维护

当前目录和标题信息至少存在于三处：

- `page-toc.yaml`
- `layouts/chrome/topmenu.html`
- `static/edit/editor.js` 中的 `PAGE_TITLES`

大更新增加、删除或移动章节后，容易出现正文、导航和编辑器页面列表不一致。

建议建立唯一站点清单，例如 `data/srd.yaml`，由它生成：

- 桌面端整站目录
- 移动端目录抽屉
- 编辑器页面列表
- 面包屑
- 上一页和下一页
- 搜索页面元数据

### 4.3 当前标题锚点不稳定

`static/js/lang-toggle.js` 会在浏览器运行时给没有 ID 的标题生成随机锚点，例如：

```text
#t-zh-h1-bksr
#t-zh-h1-ta17
```

同一个标题刷新页面后锚点会改变，因此当前链接不能可靠收藏、分享，也不能作为关键词跳转的目标。

新版应在构建阶段生成稳定 ID，例如：

```text
/core-mechanics/#action-roll
/core-mechanics/#动作掷骰
```

还应允许为标题保存旧锚点别名，避免改名后已有链接失效。

### 4.4 构建与发布不是事务式操作

当前在线保存流程存在以下风险：

- `build_srd.py` 在 Hugo 构建失败时只打印错误，没有返回非零退出码。
- `proxy_server.py` 先覆盖正式 Markdown，再尝试构建。
- 构建失败后不会恢复原内容。
- Hugo 直接写入正式 `public/`，失败时可能留下不完整产物。
- Git commit 或 push 失败会被静默忽略，不能视为可靠备份。
- 路径校验主要依靠字符串前缀判断，需要改成规范化后的真实目录归属判断。
- 编辑器切换页面或语言时没有未保存修改保护。
- 编辑器使用 `marked.js` 预览，正式站使用 Python Markdown 转换，两者可能产生不同结果。

建议将保存流程改为：

```text
接收编辑内容
    ↓
检查版本，防止覆盖他人修改
    ↓
写入临时内容目录
    ↓
在临时 public 目录完整构建
    ↓
执行结构和链接校验
    ↓
构建成功后替换正式内容与正式 public
    ↓
记录版本、时间和操作者
```

任何步骤失败时，正式内容和线上站点都不应变化。

### 4.5 前端技术和布局已经不适合继续扩展

当前页面依赖 Bootstrap 3、jQuery、Glyphicons 和固定顶栏，模板中还保留 IE8 兼容代码。

线上移动端验证中，核心机制页面的本页目录包含 30 个链接，目录在正文之前完整展开，使正文顶部位于距页面顶部约 1517 px 的位置。用户需要先滚过整段目录才能开始阅读。

此外，桌面端正文最大宽度固定在 900 px，右侧留下大量无用途空间；左侧只有当前页面标题目录，没有整站章节树。

这里不适合继续小修小补。建议保留 Hugo 模板体系，但重写页面结构、CSS 和交互脚本。

## 5. 需求逐项评估

| 需求 | 现有基础 | 评估 | 推荐实现 |
|---|---|---|---|
| 整站可折叠目录 | 只有当前页面标题目录 | 容易在现有静态站上实现 | 从唯一站点清单生成树形目录；桌面固定，移动端放入抽屉 |
| 高级 UI 与排版 | Bootstrap 3 与基础 CSS | 需要重写前端层 | Hugo 模板、现代 CSS Grid、少量原生 JavaScript |
| 标题与正文搜索 | 尚未实现 | 很适合构建期索引 | 按语言生成静态索引，客户端搜索并跳到稳定锚点 |
| 管理员在线编辑 | 已有可运行雏形 | 保留方向，重构发布流程 | 版本检查、临时构建、原子发布、失败回滚和审计记录 |
| 关键词跳转 | 尚无稳定锚点和术语表 | 可实现，但需先定义语义 | 建立术语表，在构建阶段插入链接 |
| 勘误和反馈 | 仓库已有 GitHub Issues 约定 | 实现成本低 | 页面或段落级预填 Issue；必要时再增加无 GitHub 账号表单 |

## 6. 推荐的新版阅读界面

### 6.1 桌面端

建议采用三栏信息结构：

```text
┌──────────────┬────────────────────────────┬──────────────┐
│ 整站章节树   │ 正文                       │ 本页标题目录 │
│ 可折叠       │ 限制舒适阅读行宽           │ 可选         │
│ 当前页高亮   │ 卡片、规则块、表格、图片   │ 滚动跟随     │
└──────────────┴────────────────────────────┴──────────────┘
```

- 左栏负责 CHM 式整站导航。
- 中间只负责阅读，不承载全局导航逻辑。
- 右栏只显示当前页面标题，长页面可以快速定位。
- 左右栏均可收起，给正文或宽表格腾出空间。

### 6.2 移动端

- 整站目录放入左侧抽屉，不在正文前完整展开。
- 当前页目录通过悬浮按钮或顶部按钮打开。
- 表格允许横向滚动，不压缩到不可读。
- 卡片、提示块和图片改为单列。
- 不使用大范围滚动动画，避免妨碍规则查询。

### 6.3 视觉方向

SRD 是高频查询和长文阅读工具，视觉升级应服务于信息层次，而不是做成宣传页。

建议重点投入：

- 中文正文与标题字体搭配。
- 舒适的正文行宽、行高和段落间距。
- 规则、示例、贤者恩泽、警告和数据块的稳定视觉语义。
- 表格、敌人数据、领域卡等高密度内容的专门组件。
- 柔和背景、有限强调色和少量主题插画。
- 目录展开、搜索面板和页面状态的短动画。
- 键盘焦点、减少动画偏好和对比度等无障碍支持。

不建议使用大面积玻璃拟态、过度渐变或持续滚动视差，这些效果会降低长文档的可读性。

## 7. 搜索方案

当前内容规模不需要数据库或服务端搜索。

建议在构建阶段按语言生成静态搜索索引，搜索界面提供：

- 只搜索当前语言，也允许切换语言。
- 标题权重高于正文。
- 显示命中词附近的摘要。
- 显示所属章节和页面路径。
- 搜索结果直接跳到稳定段落锚点。
- 支持键盘上下选择、`Enter` 跳转和 `Ctrl+K` 呼出。
- 搜索面板在桌面端和移动端使用同一套数据。

实现时可比较 Pagefind 和 FlexSearch。最终选择应以中文分词效果、生成索引体积和离线部署便利性为准，不应先决定库再迁就需求。

## 8. 关键词跳转方案

关键词跳转至少有两种含义，实施前需要确认：

1. 用户点击显式术语标签，跳转到规则定义。
2. 正文中出现指定术语时，系统自动把首次出现的位置转换成链接。

如果需要自动链接，建议建立显式术语表：

```yaml
terms:
  - id: advantage
    zh: 优势
    en: Advantage
    target: core-mechanics/action-roll
    anchor: advantage
    aliases:
      zh: [优势骰]
      en: []
```

构建器应遵守以下规则：

- 优先匹配最长关键词。
- 不处理代码块、标题、URL 和已有链接。
- 同一段或同一小节避免重复链接。
- 目标页面和锚点必须在构建期校验存在。
- 中英文术语分别匹配，不能跨语言误连。
- 允许为歧义词关闭自动链接，只保留显式标记。

## 9. 勘误与反馈入口

最直接的第一阶段方案是使用 GitHub Issues：

- 页面底部提供“报告本页问题”。
- 标题旁或段落工具栏提供“报告此处问题”。
- 自动预填页面标题、语言、URL、锚点和页面版本。
- Issue 模板要求填写问题类型、原文、建议修改和依据。

如果主要读者没有 GitHub 账号，再增加一个轻量反馈表单。表单只负责把结构化反馈转发给管理者，不承担内容编辑和发布职责。

反馈系统不应直接修改正文。公开反馈和管理员在线编辑应当是两条独立链路。

## 10. 推荐目标结构

```text
AGENTS.md                   # 仓库级工作规则
data/
├── srd.yaml                # 章节树、标题、顺序、URL 和别名
└── glossary.yaml           # 关键词和目标锚点
src/
├── pages/                  # 唯一正式内容源
└── imports/                # 外部大版本导入文件，不直接参与发布
assets/
├── css/                    # 源样式
├── js/                     # 源脚本
├── fonts/
└── images/
layouts/                    # 新版 Hugo 模板
scripts/
├── import/                 # 导入并生成差异，不覆盖正式内容
├── build/                  # 锚点、导航、关键词和搜索索引
└── server/                 # 在线编辑与原子发布服务
static/edit/                # 管理员编辑器
tests/                      # 构建、索引、链接和发布测试
```

统一构建关系为：

```text
src/pages + data/srd.yaml + data/glossary.yaml
                      ↓
                   构建器
                      ↓
      页面 HTML + 整站目录 + 搜索索引 + 关键词链接
```

## 11. 建议实施顺序

### 阶段 0：先建立规则

1. 在仓库根目录增加 `AGENTS.md`。
2. 编写 ADR，明确内容真相源、URL 和锚点稳定规则。
3. 定义新目录结构和生成目录的清理规则。
4. 明确新版 SRD 的导入方式，禁止直接清空正式内容目录。

验证方式：规则文档经过维护者确认，后续实现不再依赖口头约定。

### 阶段 1：加固内容与发布管线

1. 让 Hugo 构建失败正确返回非零退出码。
2. 使用临时目录构建并在成功后原子替换。
3. 构建失败时恢复原内容。
4. 增加版本冲突检查和未保存修改提醒。
5. 增加目录边界和符号链接安全检查。
6. 记录每次发布的修改文件、时间、操作者和构建结果。

验证方式：故意提交构建失败内容，线上内容和正式源文件保持不变。

### 阶段 2：统一信息架构

1. 建立唯一站点清单。
2. 从清单生成整站树形目录和编辑器页面列表。
3. 生成稳定页面 URL、稳定标题锚点和旧锚点别名。
4. 增加断链和重复锚点检查。

验证方式：任意新增一章只修改站点清单和对应正文，导航、编辑器和前后页自动同步。

### 阶段 3：重做阅读界面

1. 重写 Hugo 布局。
2. 移除 Bootstrap 3、jQuery 和旧图标字体。
3. 完成桌面三栏和移动端目录抽屉。
4. 设计规则块、示例块、贤者恩泽、表格和数据卡片。
5. 加入响应式、键盘操作和无障碍支持。

验证方式：桌面、平板和手机尺寸均可在首屏直接开始阅读，目录不会把正文推到首屏之外。

### 阶段 4：搜索与关键词

1. 生成中英文搜索索引。
2. 完成搜索面板和快捷键。
3. 建立术语表。
4. 加入关键词自动链接与目标校验。

验证方式：标题和正文搜索均能跳到稳定锚点；不存在指向无效目标的关键词链接。

### 阶段 5：反馈与大版本迁移

1. 加入页面级和段落级反馈入口。
2. 完善 Issue 模板和管理标签。
3. 使用只生成差异的导入工具迁入新版 SRD。
4. 人工审查内容差异后再发布。

验证方式：反馈自动携带页面和锚点信息；新版内容迁移不会覆盖既有勘误。

## 12. 验证结果与限制

本次只读调研完成了以下验证：

- 检查了仓库结构、构建脚本、模板、样式、在线编辑器和代理服务。
- 检查了线上首页、长章节桌面布局和移动端布局。
- 验证了当前运行时锚点刷新后会变化。
- 运行 `scripts/test_proxy_server.py`，结果为 `16 passed`。

现有测试没有覆盖：

- Hugo 失败是否正确传递到保存接口。
- 构建失败后的内容回滚。
- `public/` 原子替换。
- 多管理员同时编辑的冲突。
- 符号链接和目录边界攻击。
- 搜索、导航和关键词索引完整性。

本机当前没有可执行的 Hugo，因此本次没有完成本地全站构建验证。

## 13. 最终建议

本次翻新应以“文档系统重构”而不是“换一套网页皮肤”立项。

第一优先级不是视觉稿，而是先解决：

1. 唯一内容源。
2. 唯一目录数据源。
3. 稳定 URL 和锚点。
4. 可回滚的在线发布。

这四项稳定后，再进行整站目录、现代排版、搜索、关键词和反馈功能的实现。这样既能保留现有内容与部署优势，也不会把新版 SRD 建立在当前容易失同步和不可回滚的基础上。
